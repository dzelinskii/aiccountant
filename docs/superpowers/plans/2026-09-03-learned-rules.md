# Правила, выученные из подтверждений — план реализации

> **Для агентов:** ОБЯЗАТЕЛЬНЫЙ СУБ-СКИЛЛ — использовать
> superpowers:subagent-driven-development (рекомендуется) или
> superpowers:executing-plans. Шаги помечены чекбоксами.

**Цель:** система запоминает решения человека — подтвердил категорию, и такие же
операции дальше раскладываются сами, без обращения к языковой модели.

**Архитектура:** при подтверждении категории создаётся или обновляется правило
«описание → категория» с пометкой `learned`. Ручные правила выученными не
перезаписываются. Уже лежащие операции без категории разбираются **по согласию
человека**: интерфейс спрашивает, сколько таких нашлось, и предлагает разложить.

**Стек:** FastAPI, SQLAlchemy 2 async, Pydantic v2, pytest + testcontainers;
фронтенд — React 19, Mantine, vitest.

**Спека:** `docs/superpowers/specs/2026-09-03-learned-rules-design.md`

**Ветка:** `learned-rules` (уже создана).

- [ ] **Шаг 3: Обучение**

В `backend/app/ledger/service.py` добавить функцию рядом с остальными про

```python
async def learn_rule_from(
    db: AsyncSession, workspace_id: uuid.UUID, transaction: Transaction
) -> None:
    """Запомнить решение человека: описание операции даёт эту категорию.

    Ручное правило не трогаем — тот, кто завёл его сам, знал что делает и не
    ждёт, что оно поменяется от правки одной операции. Выученное обновляем
    свободно: последнее подтверждение и есть текущее намерение.
    """
    if transaction.category_id is None or not transaction.merchant:
        return
    normalized = normalize_description(transaction.merchant)
    if not normalized or len(normalized) > RULE_TEXT_MAX_LENGTH:
        return
    existing = await repository.find_description_rule(db, workspace_id, normalized)
    if existing is not None:
        if existing.source == "manual":
            return
        existing.category_id = transaction.category_id
        return
    repository.add_description_rule(
        db,
        DescriptionRule(
            workspace_id=workspace_id,
            normalized_text=normalized,
            category_id=transaction.category_id,
            source="learned",
        ),
    )
```

- [ ] **Шаг 3: Repository**

В `backend/app/ledger/repository.py` добавить две функции. Обе фильтруют по
`workspace_id` — утечка между workspace считается в этом проекте критическим
багом, и фильтр живёт здесь, а не в сервисе.

Первая считает операции без категории с заданным нормализованным описанием,
исключая одну заданную. Сравнение описания — по тому же правилу нормализации,
что и у правил; чтобы не тащить нормализацию в SQL, сравнивать нормализованное
значение из Python с нормализованным в запросе через `func.lower(func.trim(...))`
нельзя (схлопывание внутренних пробелов и NFC так не выразить). **Поэтому:**
выбирать кандидатов по `merchant IS NOT NULL` и `category_id IS NULL` в пределах
workspace, а нормализацию и сравнение делать в Python.

Это осознанный размен: выборка операций без категории в одном workspace мала,
а попытка выразить нормализацию в SQL развела бы два определения одного правила.

Вторая функция проставляет категорию списку операций по их идентификаторам.

- [ ] **Шаг 4: Сервис**

Две функции: подсчёт похожих и разбор похожих. Обе принимают идентификатор
