# Кредитный лимит и «сколько могу потратить» — план реализации

Исполнение спеки `docs/superpowers/specs/2026-09-15-credit-limit-design.md`
(продолжает `2026-09-11-credit-card-balance-design.md`, где остатком кредитки
стала чистая позиция). Работа сквозная: коллектор → договор импорта → хранение →
выдача → экран. Порядок задач — снизу вверх, чтобы каждая проверялась своими
тестами, а не следующей.

Общие правила исполнения (из CLAUDE.md), обязательны для каждой задачи:

- **Мутационное ревью тестов** — критерий приёмки: после реализации внести
  дефект в код и показать, какой тест на него падает. Зелёный прогон
  доказательством не считается.
- Деньги — строка на границах и `Decimal`/BigInt внутри; `float` запрещён,
  включая тесты.
- Слова банка живут только в `plugins/<банк>/map.ts`, наружу едет `creditLimit`.
- Правка поведения — правка справочника в том же изменении (иначе docs-gate).
- Перед «готово» задачи прогнать то же, что гоняет CI. Бэкенд (из `backend/`):
  `uv run ruff check .`, `uv run ruff format --check .`, `uv run mypy`,
  `uv run lint-imports`, `uv run pytest`. Коллектор и фронт (из своих папок):
  `pnpm lint`, `pnpm build`, `pnpm test`.

В логи не идут ни суммы, ни лимиты — только идентификаторы (импорта, карты).

## Task 1: Контракт коллектора

**Файлы:** `collector/src/core/contract.ts`, `collector/src/runner/push.ts`
(+ `push.test.ts`).

- `CollectedAccount` получает `creditLimit: string | null` — «лимит строкой, как
  отдал банк; `null` — не кредитка или банк лимита не сообщил».
- `requestBody` в `push.ts`: если `account.creditLimit !== null`, класть в блок
  счёта `credit_limit`. Блок по-прежнему не отправляется вовсе, когда нет
  остатка (лимит без остатка бессмыслен — «доступно» из него не посчитать).

**Приёмка / мутации:**
- Тест: счёт с лимитом уезжает с `credit_limit`; убрать поле в коде — падает.
- Тест: счёт без лимита уезжает **без ключа** `credit_limit` (не `null`):
  отсутствие поля и «банк сказал, что лимита нет» — разные вещи, и схема
  импорта различает их. Подставить `null` в коде — падает.
- Тест: лимит есть, остатка нет — блока счёта нет вовсе.

## Task 2: Т-Банк — лимит из ответа

**Файлы:** `plugins/tbank/map.ts` (+ `map.test.ts`).

`resolveBalance` уже читает `creditLimit` ради чистой позиции. Рядом —
`resolveCreditLimit(item)`: у счёта с `accountType === 'credit'` вернуть
`creditLimit.value` строкой, иначе `null`. Константа `CREDIT_CARD_ACCOUNT_TYPE`
переиспользуется, второй её копии не заводить.

**Приёмка / мутации:**
- Тест на фикстуре кредитки: лимит собран строкой.
- Тест: у дебетового счёта `creditLimit === null` — снять проверку типа в коде,
  тест падает.
- Тест: блока `creditLimit` нет → `null`, и остаток при этом тоже `null`
  (поведение из предыдущей работы не сломано).

## Task 3: Сбербанк — лимит из той же ручки

**Файлы:** `plugins/sber/map.ts` (+ `map.test.ts`).

Лимит приходит блоком `creditType.creditLimit` той же ручкой `cardInfo`, которую
`index.ts` уже зовёт ради долга (`creditInfo`). Нового запроса не нужно, менять
`index.ts` не нужно. Поле уже лежит в записанной фикстуре живого ответа —
`plugins/sber/index.test.ts:266`, `creditLimit: { amount: '150000.00' }`, — так
что форма блока не догадка.

В `map.ts` рядом с `cardBalance` — `cardCreditLimit(item, id, creditByCard)`:
только для `cardTypeKind(item) === 'credit'`, значение —
`moneyAmount(getRecord(credit, 'creditLimit'))`.

**Приёмка / мутации:**
- Тест: у кредитки лимит собран; у дебетовой — `null`.
- Тест: `cardInfo` не ответил (карты нет в `creditByCard`) — лимит `null`, и
  сбор не падает; так же, как сейчас с остатком.
- Мутация: вернуть лимит при `kind === 'unknown'` — тест падает.

## Task 4: Альфа-Банк — лимит выводится

**Файлы:** `plugins/alfa/map.ts` (+ `map.test.ts`).

Прямого поля нет. Лимит = `amount − total`: по разведке (§5.1–5.2)
`amount = лимит + currentBalance − holds`, `total = currentBalance − holds`,
холды сокращаются. Вычитание — `subtractDecimal` из `core/money.ts`, значения —
через тот же `signedMinor`, что и остаток.

Считать **только у кредитного счёта** — `properties.creditCardAccount === true`.
У дебетового `amount == total`, и без этой проверки каждый счёт получил бы
лимит `0.00` — число, неотличимое от настоящего.

**Приёмка / мутации:**
- Тест на фикстуре кредитки (`type:"EG"`, `creditCardAccount:true`): лимит
  совпадает с живым числом разведки.
- Тест: дебетовый счёт (`EE`) — `creditLimit === null`. Снять проверку
  `creditCardAccount` — тест падает (счёт получает `0.00`).
- Тест: холды ненулевые — лимит тот же (завести фикстуру, где `holds` отличен
  от нуля). Это проверка самой формулы, а не арифметики. **Сокращение холдов —
  вывод из описания полей в разведке §5.2, а не замер:** живые числа спеки
  сошлись на карте, про холды которой ничего не известно. Проверить на живом
  прогоне (Task 11) и, если не сойдётся, вернуться к формуле.
- Мутация: поменять операнды местами (`total − amount`) — тест падает.

## Task 5: Договор импорта

**Файлы:** `backend/app/imports/schemas.py`, `backend/app/imports/service.py`
(+ `tests/test_imports_parsed.py`).

- `ParsedAccountIn` получает `credit_limit: MoneyStr | None = None` и тот же
  валидатор «не float», что у `balance`: через число деньги не проходят.
- `_payload_account` возвращает третьим значением лимит. Кортеж из трёх —
  уже не читается; ввести `NamedTuple` (`ReportedAccount`) с полями
  `balance`, `card_masks`, `credit_limit`.
- **Строгость на входе, снисходительность при подтверждении** — тот же приём,
  что у меток карт: схема отвергает мусор (422), а `_payload_account`,
  перечитывая JSONB, негодный лимит **отбрасывает** с `logger.warning`
  (`import_broken_credit_limit`, только `import_id`). Порча остатка
  по-прежнему роняет разбор: остаток — деньги счёта, лимит — пояснение к нему.

**Приёмка / мутации:**
- Тест: импорт с лимитом принят, лимит сохранён в разборе.
- Тест: лимит числом JSON → 422 (как у остатка).
- Тест: в сохранённом разборе лимит — мусор (`"много"`, список, `None`) →
  подтверждение проходит, операции на месте, лимит не применён, в логе запись.
  Мутация: заставить `_payload_account` падать на мусоре — тест падает.
- Тест: порча остатка по-прежнему роняет разбор (регресс не сломан).

## Task 6: Хранение наблюдений

**Файлы:** `backend/app/ledger/models.py`,
`backend/alembic/versions/0014_credit_limit.py`,
`backend/app/ledger/repository.py` (+ `tests/test_migrations.py` уже проверяет
прогон миграций).

Таблица `credit_limit_observations`:

| колонка | тип | смысл |
|---|---|---|
| `id` | UUID PK | |
| `workspace_id` | UUID | как у всех доменных таблиц, фильтр в repository |
| `account_id` | UUID → `accounts.id` | |
| `value` | `NUMERIC(20, 4)` | лимит |
| `observed_at` | timestamptz | когда значение замечено **впервые** |
| `confirmed_at` | timestamptz | когда подтверждено в **последний** раз |

Индекс по `(workspace_id, account_id, confirmed_at DESC)` — чтение всегда
«последнее наблюдение счёта».

Два момента, а не один, — решение спеки §5: без `confirmed_at` экономия на
записях («повтор новой строки не создаёт») столкнулась бы с проверкой свежести
(«лимит замечен тем же сбором, что остаток») и выдала бы живой лимит за
устаревший.

Функции repository:

- `latest_credit_limit(db, workspace_id, account_id)` — последнее наблюдение
  счёта или `None`;
- `latest_credit_limits(db, workspace_id)` — `dict[account_id, наблюдение]`
  одним запросом (`DISTINCT ON`), для списка счетов и дашборда: по запросу на
  счёт — N+1 на каждый показ главного экрана;
- `add_credit_limit_observation(...)` — без commit, как и всё в repository.

**Приёмка / мутации:**
- Тест: наблюдения чужого workspace не видны (утечка между workspace —
  критический баг). Убрать фильтр в коде — тест падает.
- Тест: `latest_credit_limits` возвращает по счёту **последнее** наблюдение при
  трёх строках у одного счёта. Мутация: убрать `DESC` — падает.
- Тест: счёт без наблюдений в словаре отсутствует (а не приходит с `None`).

## Task 7: Применение при подтверждении

**Файлы:** `backend/app/ledger/service.py`, `backend/app/imports/service.py`
(+ `tests/test_account_balance.py` или новый `tests/test_credit_limit.py`).

`apply_reported_balance` получает параметр `credit_limit: Decimal | None` и
записывает наблюдение **в той же транзакции**, что остаток, — иначе лимит и
остаток разъедутся во времени, а «доступно» считается из обоих. Момент —
`imp.created_at`, тот же, что у остатка.

Правила записи (спека §5), все в `service.py`, не в repository:

1. `credit_limit is None` → ничего не делать; прежние наблюдения не трогать.
2. Наблюдений нет → добавить строку (`observed_at = confirmed_at = момент`).
3. Последнее наблюдение с тем же значением → **новой строки нет**, у неё
   двигается `confirmed_at`.
4. Значение изменилось → новая строка.
5. Момент импорта **не позже** `confirmed_at` последнего наблюдения → не делать
   ничего: наблюдение из прошлого не переписывает настоящее. Тем же правилом,
   по которому не едет назад остаток (проверка `reported_at` на строке выше).

Важно: сейчас `apply_reported_balance` **выходит из функции**, когда остаток не
едет назад (ранний `return`). Лимит после этого тоже применять не нужно — они
из одного сбора, и оба устарели. Порядок проверок сохранить, чтобы правило 5 не
оказалось недостижимым.

**Приёмка / мутации:**
- Тест: первый сбор с лимитом — одна строка, `observed_at == confirmed_at`.
- Тест: **повторный сбор с тем же лимитом новой строки не создаёт, но двигает
  `confirmed_at`**. Мутация: не двигать `confirmed_at` — падает вместе с
  главным тестом Task 8.
- Тест: изменившийся лимит добавляет строку, прежняя остаётся с прежними
  моментами (история изменений читается по `observed_at`).
- Тест: сбор без лимита строк не создаёт и не стирает прежние.
- Тест: импорт с моментом раньше последнего наблюдения ничего не меняет.
  Мутация: убрать сравнение моментов — падает.
- Тест: лимит применяется **и при нуле новых операций** — повторный сбор
  законный способ обновить лимит, и он же самый частый.

## Task 8: Выдача наружу

**Файлы:** `backend/app/ledger/balance.py`, `service.py`, `schemas.py`,
`router.py` (+ `tests/test_accounts_api.py`, `tests/test_dashboard_api.py`).

Правило «доступно» — чистой функцией в `balance.py`, рядом с `visible_balance`:

    def credit_available(limit, limit_at, reported_balance, reported_at) -> Decimal | None

Возвращает `limit + reported_balance`, **только** когда все четыре значения есть
и `limit_at == reported_at`; иначе `None`. Складываем именно `reported_balance`,
а не видимый остаток: у счёта с наблюдением лимита остаток всегда от источника,
а поправка, введённая руками, к банковскому лимиту отношения не имеет.

Отрицательный результат не обрезается: карта сверх лимита — факт, а не ошибка
расчёта.

`AccountOut` и `DashboardAccount` получают три поля:

- `credit_limit: MoneyStr | None` — последний известный лимит;
- `credit_limit_at: datetime | None` — момент его последнего подтверждения;
- `credit_available: MoneyStr | None` — «доступно», `None` когда не считается.

Считает бэкенд, а не фронт: сложение денег в JS — это `float`, который запрещён.

`list_accounts`, `create_account`, `update_account` в `service.py` возвращают вид
счёта одинаково — иначе переименование карты в модалке стёрло бы лимит с
экрана до перезагрузки страницы.

**Приёмка / мутации:**
- **Главный тест смысла:** остаток свежий, последнее наблюдение лимита старее —
  `credit_available is None`, а `credit_limit` и `credit_limit_at` отданы.
  Мутация: сравнивать не моменты, а «лимит есть» — падает. Без этого теста вся
  конструкция бессмысленна: число, собранное из двух разных сборов, выглядит
  достоверно.
- **Сверка смысла на живых числах трёх банков** (записанные в спеке §2):
  150 000 / −148 063.81 → 1 936.19; 142 000 / −2 000.47 → 139 999.53;
  53 000 / −51 025 → 1 975. Тест стережёт саму идею одного хранимого поля.
- Тест: лимит ниже долга → отрицательное «доступно», не ноль. Мутация:
  `max(0, …)` — падает.
- Тест: счёт без наблюдений отдаёт три `None` и выглядит как раньше.
- Тест: сумма по счетам на дашборде **не изменилась** — она считается по
  остаткам, и эта работа её не трогает.
- Тест: `update_account` (переименование) отдаёт лимит на месте.

## Task 9: Экран

**Файлы:** `frontend/src/api/ledger.ts`,
`frontend/src/components/AccountBalance.tsx` (новый),
`frontend/src/pages/AccountsPage.tsx`, `frontend/src/pages/DashboardPage.tsx`
(+ тесты страниц и компонента).

Сейчас блок остатка написан дважды — в `AccountsPage` и в `DashboardPage`.
Добавить лимит в обе копии значит завести два места для одного утверждения.
Сначала вынести общий компонент, затем менять его один раз.

`AccountBalance` показывает:

- есть `credit_available` → главное число **«доступно / лимит»**, например
  `1 936.19 / 150 000`; остаток (чистая позиция) — строкой ниже, вместе с
  моментом, как сейчас;
- лимит есть, «доступно» нет → главным остаётся остаток, лимит показан с
  пометкой, на какой момент он известен (`credit_limit_at`) — **«замечен
  такого-то»**, а не «изменён»: банк сообщает лимит только в момент сбора, и
  выдавать это за дату его решения нельзя;
- лимита нет → как сейчас, ничего не меняется.

**Приёмка / мутации:**
- Тест компонента: кредитка с «доступно» показывает оба числа и не теряет
  остаток. Мутация: перепутать местами «доступно» и лимит — падает (числа в
  тесте разные и не переставляемые молча).
- Тест: лимит без «доступно» — число «доступно» на экране отсутствует, а
  пометка о моменте есть. Это экранный близнец главного теста Task 8.
- Тест: обычный счёт выглядит как раньше (снимок существующего поведения).
- Тест: обе страницы используют компонент — достаточно того, что тесты
  `AccountsPage` и `DashboardPage` на кредитке видят одно и то же.
