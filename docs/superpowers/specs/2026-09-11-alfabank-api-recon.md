# Альфа-Банк — результаты разведки API личного кабинета

Дата: 2026-09-11. Статус: справочные данные разведки, решением не является.

> Это решение на дату выше. Текущее состояние системы — `docs/reference/`.

Это **не спека**, а её фактическая основа: что банк отдаёт, чем авторизует и
где расставлены грабли. Решений здесь нет намеренно — они принимаются
отдельно, после брейншторма. Спеки двух готовых коллекторов, на которые идут
ссылки:

- Т-Банк: `docs/superpowers/specs/2026-09-01-tbank-collector-design.md`
- Сбербанк: `docs/superpowers/specs/2026-09-08-sberbank-collector-design.md`
  (и его разведка `2026-09-08-sberbank-api-recon.md`).

## 1. Как собирались факты

Живой личный кабинет владельца, Яндекс.Браузер с отладчиком, только чтение.
Человек логинился сам; в форму входа не вмешивались. Структура ответов и формы
запросов извлекались скриптом внутри страницы (`fetch` к same-origin API с
куками сессии) — значения наружу не выносились: в этом документе нет ни сумм,
ни описаний, ни номеров карт и счетов. Образцы формата маскированы: цифры → `9`,
буквы → `a`, хвосты номеров — `····9999`.

Проверялось на живом наборе: 7 счетов, 6 карт, история операций за полгода
(последние ~100 операций разобраны детально). Всё, что ниже помечено как
«не проверено», таковым и является.

## 2. Доступ к сайту: тот же корень Минцифры, что у Сбера

Весь домен Альфы (`web.alfabank.ru`) выпущен через `Russian Trusted Sub CA` —
**тот же корень УЦ Минцифры, которым подписан Сбер**. Проверено делом: цепочка
`web.alfabank.ru` строится от `Russian Trusted Root CA`, корня нет ни в
хранилище Windows, ни в штатном Chrome (`SELF_SIGNED_CERT_IN_CHAIN`).

Отпечаток корня и открытого ключа совпали с константами, уже зашитыми в
`collector/src/runner/trust-anchor.ts`, байт в байт:

    SHA-256:    d26d2d0231b7c39f92cc738512ba54103519e4405d68b5bd703e9788ca8ecf31
    SPKI (b64): ArgiDAcHKNt3HZrFnlRSHE7drSGng7smz98ZwdsPrjc=

**Следствие:** якорь доверия к УЦ и закрепление ключа в окне входа
(`certificateArgs` в `browser.ts`) переиспользуются без единой правки. Для Сбера
на это уходила отдельная задача плана — здесь её нет.

## 3. Авторизация

### 3.1 Что установлено

Вход — через **OpenID Connect** (`private.auth.alfabank.ru/passport/...`,
`client_id=newclick-web`, `response_type=code`, `scope=openid`). После входа
authorization code обменивается на сессию, и пользователь оказывается на
`https://web.alfabank.ru/dashboard`. Это отличается от Сбера и Т-Банка, где вход
был обычной формой; **признак успешного входа — переход на `/dashboard`**.

Сессия держится **на куках**. Заголовка `Authorization` нет; токена в query нет.

**Минимальный набор — две куки из 38, измерено клиентом `node:https`** (перебор
подмножеств настоящими куками, снятыми из браузера через CDP):

| Кука | Флаг | Роль — установлено перебором |
|---|---|---|
| `GW_SESSION_AO` | `httpOnly`, сессионная | **сама сессия.** Убери — `302` (редирект на вход). Одной её хватает на чтение |
| `XSRF-TOKEN` | видна JS, сессионная | нужна **только для POST** (двойная отправка в заголовок `x-xsrf-token`); без неё чтение живёт, а `POST /operations` даёт `403` |

Проверено, что именно эти две и только они: `GW_SESSION_AO`+`XSRF-TOKEN` →
`GET=200, POST=200`; `SUCAO`+`XSRF-TOKEN` без `GW_SESSION_AO` → `302/302`
(значит `SUCAO` сессию не держит); всё остальное (`passport-session`,
`newclick-sticky-cookie`, `DEVICE_*`, антифрод, аналитика) выкидывается без
последствий. `GW_SESSION_AO` — `httpOnly`: со страницы её не взять, из cookie
jar (CDP/Playwright) — да. Это тот же вывод, что и у Сбера.

**Долгоживущие токены — зацепка для переиспользования сессии.** В jar есть
`access_token` и `cross_auth_token` — обе `httpOnly` и **персистентные**
(срок ~3 месяца, до 2026-12-10), в отличие от сессионной `GW_SESSION_AO`. На
живые запросы они не влияют (минимальный набор без них работает), но по виду —
токены обновления OIDC: то, чем короткую `GW_SESSION_AO` можно продлевать без
повторного входа человека. Механику обновления разведка не разбирала —
проверяется, когда `GW_SESSION_AO` умрёт (см. §7). Если подтвердится, это
снимает у Альфы ту боль, что осталась у Сбера (короткая сессия без продления).

**Как со Сбером: сессия — в `httpOnly`-куках.** Скрипты страницы их не видят, но
владелец cookie jar (Playwright, Electron, нативный CookieManager) — видит.
Значит, секрет забирается из браузера, а не со страницы. Это тот же вывод, что
дал коллектор возможным на мобильных оболочках без Playwright.

Видны для JS (не httpOnly) и уходят на API ещё: `DEVICE_APP_ID`,
`DEVICE_SECRET`, `DEVICE_PUBLIC_KEY_ID` (привязка устройства), `XSRF-TOKEN`
(см. ниже), плюс аналитика (`_sp_*`, `TS…` от BIG-IP) и антифрод (см. 3.3).

### 3.2 XSRF обязателен на запись — проверено

Все доменные ручки — `POST`. Запрос без заголовка `x-xsrf-token` получает
**403**; тот же запрос с заголовком — **200**. Проверено на
`operations-history/operations`.

Схема — двойная отправка: значение берётся из куки `XSRF-TOKEN` (она видна JS,
не httpOnly) и повторяется в заголовке `x-xsrf-token`. Для клиента вне браузера
это тривиально: прочитать куку `XSRF-TOKEN` из jar и продублировать в заголовок.

### 3.3 Антифрод Group-IB на чтении не проверяется — проверено

Браузер шлёт на каждый запрос заголовки `x-gib-gsscw-alfabank-retail` и
`x-gib-fgsscw-alfabank-retail` (зеркала кук `gsscw-*`/`fgsscw-*`), генерируемые
обфусцированным скриптом Group-IB. **Все запросы этой разведки шли без этих
заголовков и всё равно получали 200.** Значит, на читающих ручках антифрод-
**заголовки** не enforced — а именно их клиент вне браузера сгенерировать не
может. Это снимает главный риск переносимости.

Оговорка честно: антифрод-**куки** (`gsscw-*`, `fgsscw-*`, `cfidsw-*`,
`__zzatw-*`) в jar при этом присутствовали. Нужны ли они серверу — часть
вопроса о минимальном наборе кук (§7), который на этой разведке не закрыт.

## 4. Операции: `POST /api/v1/operations-history/operations`

Единственная ручка истории, отдаёт операции по всем счетам сразу. Тело:

    {"size": 100, "page": 1, "forced": false,
     "from": "9999-99-99", "to": "9999-99-99",
     "filters": [{"type": "accounts", "values": ["99999999999999999999"]}]}

Проверено опытом:

- **Пагинация — `page`/`size`, страницы с 1.** Максимум `size` — **100**:
  `size:100` отдаёт 100, `size:150` → 400. Листать `page`, пока страница короче
  `size`. Поля `pagesInfo:{page,size}` в ответе есть, общего числа операций нет.
- **Фильтр дат — верхнеуровневые `from`/`to`, формат `ГГГГ-ММ-ДД`, обе границы
  включительно.** `from=to=«один день»` вернул ровно операции того дня;
  `«1–31 августа»` — операции строго этого окна. Границы — календарные сутки в
  часовом поясе банка (время в ответе с офсетом `+0300`). Вложенный
  `filters:[{type:"period",...}]` и поля `dateFrom/dateTo` **не работают**
  (первый вернул 0, вторые проигнорированы) — не использовать.
- **Фильтр счёта — `filters:[{type:"accounts","values":[НОМЕР_СЧЁТА]}]`.**
  Значение — 20-значный **номер счёта**, не внутренний id. Так реализуется
  `fetchOperations(accountId=номер счёта)`.

### 4.1 Форма операции

    {
      "id":            "9999999aaaa#aa9999999",   // стабильный id — external_id
      "operationId":   "aaaaaaaa-....-....",       // GUID, не нужен
      "clickReference":"a999999999999999",         // связь ног перевода (см. 4.3)
      "dateTime":      "9999-99-99T99:99:99.999+0300", // ISO с офсетом
      "title":         "…",                        // человекочитаемое описание
      "comment":       "…",                        // опционально
      "amount": {"value": 999999, "currency": "RUR", "minorUnits": 100},
      "direction":     "EXPENSE" | "INCOME",       // знак явный
      "mcc":           "9999",                     // опционально, на карточных
      "category": {"id": "99999", "name": "…"},    // PFM-категория Альфы
      "status":        "SUCCESS",
      "actions":       [ { "type": "REPEAT", "operationType": "…" }, … ]
    }

- **Деньги — целое `value` в минорных единицах + делитель `minorUnits`.**
  `value/minorUnits` даёт сумму (сдвиг на 2 разряда при `minorUnits:100`).
  `value` целое → в `Decimal` без `float`; при разборе тянуть его строкой
  (общий lossless-JSON), делить строковой арифметикой.
- **Валюта — `RUR`** (устаревший ISO-код рубля, ныне `RUB`) — нормализовать
  в `RUB`. Встречается и `CNY` (мультивалютный счёт, §5).
- **Направление явное** — `direction`, знак не выводится из ресурса (в отличие
  от Сбера).
- **external_id — поле `id`.** Оно же в `deepLink` карточки операции; содержит
  `@`, `#`, буквы — строка, не число.

### 4.2 Подсказка о категории — два источника

- `mcc` — есть на карточных операциях; общий словарь `hintFromMcc` (как у обоих
  банков), формат в плагине не проверяется.
- `category.id` — таксономия Альфы (`"00025"` прочие расходы, `"00052"`/`"50009"`
  переводы, `"50002"` зарплата, `"50013"` пополнения, …). Это **свои коды
  банка**, им нужна таблица перевода в плагине — как формы у Сбера. MCC
  надёжнее там, где он есть; `category.id` — запасной источник, когда MCC нет.

### 4.3 Переводы себе — без привязки к счёту в самой операции

Важная особенность: **в операции нет поля счёта.** История глобальная, привязка
достигается только фильтром `accounts`. Поэтому механика переводов себе иная,
чем у Сбера (где были `fromResource`/`toResource`):

- **Карта→карта внутри Альфы** — две записи с одним `clickReference`
  (одна `INCOME`, одна `EXPENSE`), `actions[].operationType = CARD2CARD_TRANSFER`.
- **Перевод себе в другой банк (СБП)** — одна нога `EXPENSE`,
  `operationType = FAST_PAYMENT_SYSTEM_TRANSFER_ME2ME`, `title` начинается с
  «Перевод себе в другой банк». Вторая нога — в чужом банке, здесь её нет.

При сборе по конкретному счёту (фильтр `accounts`) каждая нога естественно
приезжает на своём счёте: расход — на счёте-источнике, приход — на счёте-
получателе. Как это ложится на существующее спаривание переводов из работы по
Сберу — решать в спеке.

## 5. Счета и карты — чистый REST, без RSocket

Дашборд целиком на виджетах, и виджета «Мои продукты» в его разметке нет —
данные счетов грузятся отдельными ручками. RSocket (`rsocket-transport/encrypt`)
в трафике мелькал, но счета доступны и по обычному REST — websocket для них не
понадобился. Обе ручки нашлись при заходе в карточку счёта:

- **`GET /api/v1/account/`** (со слэшем, без параметров) — **все счета** одним
  массивом `accounts`. Это список для `fetchAccounts`. С `?accountNumber=…`
  отдаёт один. Без слэша (`/api/v1/account`) — 404: слэш значим.
- **`GET /api/v1/cards/masked-cards`** (без параметров) — **все карты**, у каждой
  `account.number` — привязка к счёту. С `?accountNumber=…` — карты одного счёта.

### 5.1 Форма счёта (`accounts[]`)

    {
      "number":         "99999999999999999999",  // 20-значный номер, id счёта
      "amount":         {"value": …, "currency": "RUR", "minorUnits": 100},
      "total":          {"value": …, …},
      "holds":          {"value": …, …},
      "currentBalance": {"value": …, …},
      "properties": {"creditCardAccount": false, "mainAccount": true, …},
      "type":           "EE",              // EE/EH текущий, EG кредитка, GK брокерский
      "description":    "Текущий счёт",
      "creditProductType": "OVERDRAFT" | "ANNUITY" | …,
      "comboData":      { … } | отсутствует
    }

### 5.2 Остаток кредитки — та же ловушка, что у Сбера

На кредитном счёте (`properties.creditCardAccount:true`, `type:"EG"`) поля
расходятся по смыслу — проверено на двух живых кредитках:

- `amount` — **доступно к трате**, то есть лимит плюс собственные минус холды.
  Показал бы **заёмные деньги как собственные** — брать нельзя (аналог
  `availableLimit` у Сбера).
- `total` — **чистая собственная позиция**: у кредитки с долгом ушёл в минус
  (`total = currentBalance − holds`). Честный остаток — это `total`
  (или `currentBalance`), не `amount`.

На дебетовом счёте `amount == total == currentBalance` (когда нет холдов), так
что различие значимо только для кредиток — но значимо. Выбор поля — решение
спеки; разведка лишь показывает, что `amount` тут врёт.

### 5.3 Мультивалютный счёт — номер не уникален

Брокерский счёт пришёл **дважды с одним номером**, но разными валютами (`RUR` и
`CNY`) — по под-балансу на валюту. **Номер счёта не уникален**, различает
валюта. Для `CollectedAccount.id` номера мало: нужен номер + валюта. Брокерские
(`GK`) — инвестиционные, истории операций по ним нет; вероятно, их вообще
исключить (решать в спеке).

### 5.4 Форма карты (`cards[]`)

    {
      "number":        "999999******9999",  // маска, последние 4 — cardMask
      "isCredit":      false,
      "account": {"number": "99999999999999999999"},  // привязка к счёту
      "paymentSystem": "NSPC",
      "title":         "Альфа-карта МИР",
      "type":          "RR" | "NH" | "RG" | "R7" | …,
      "status": {"isActive": true, "isBlocked": false, …}
    }

`cardMasks` счёта — последние 4 символа `number` карт, у которых
`account.number` совпадает с номером счёта.

## 6. isAlive и обнаружение протухшей сессии

`GET /api/v1/account/` годится сигналом живости: **200 — жива, 302 — мертва**.
Проверено клиентом `node:https` без кук: ручка отдаёт `302` (редирект на вход
OIDC), а не `401/403`. То есть `isAlive` смотрит на `200` против `302`;
редиректы клиент проходить не должен, иначе примет страницу входа за успех.
Запрос без `x-xsrf-token` даёт `403`, но это про отсутствие токена, а не про
смерть сессии, — на GET-ручку XSRF не влияет. Что отдаёт именно истёкшая (а не
отсутствующая) сессия, подтвердит первый живой прогон, но 302 — уже наблюдённый
факт, а не догадка.

## 7. Что осталось открытым (не проверено)

1. **Срок жизни `GW_SESSION_AO` — коротко, ~15–30 минут (грубо).** Две точки
   реплея сохранённого секрета клиентом `node:https`: жива в 10:05 (уже после
   закрытия браузера — значит дело в сроке, не в закрытии окна), мертва в 10:20
   (`302`). Вход был ~09:5x. Короче даже Сбера. Точный замер (частый опрос при
   живом входе) не делался — для вывода «без продления вход почти каждый раз»
   этого достаточно.
2. **Обновление сессии персистентными токенами.** `access_token` /
   `cross_auth_token` живут ~3 месяца — проверить, можно ли ими воскресить
   истёкшую `GW_SESSION_AO` без входа человека (обмен на OIDC-эндпоинте).
   Это ключ к долгой сессии; проверяется, когда `GW_SESSION_AO` умрёт.
3. **Код истёкшей сессии** для `isAlive`: без кук — `302` (§6); что отдаёт
   именно протухшая `GW_SESSION_AO` (302 или 401), подтвердить на мёртвой.
4. **Быстрый вход по ПИН — наблюдён.** Заход на `web.alfabank.ru` из
   сохранённого профиля браузера ведёт не на телефон+СМС, а на
   `/passport/.../pincode` (быстрый вход): профиль помнит устройство. Молчаливого
   входа из одних кук нет (фактор всё же спрашивают), но повторный вход дешёвый.
   QR-вход из приложения как ещё один путь — не разбирался.
5. **Мобильное API приложения** — записано в беклог как способ починить срок
   жизни сессии; вскрытие требует MITM и обхода закрепления в приложении,
   к вебу отношения не имеет.

Пункт про минимальный набор кук из открытых вопросов **снят**: измерено (§3.1) —
`GW_SESSION_AO` + `XSRF-TOKEN`.

## 8. Вердикт

Коллектор вне браузера **реализуем — как у Сбера**. Доказано на живом кабинете:

- сессия — в `httpOnly`-куках cookie jar, не на странице;
- обычный HTTP-клиент банк пускает; антифрод-**заголовки** на чтении не нужны;
- корень УЦ Минцифры и его закрепление переиспользуются из кода Сбера без правок;
- история, счета и карты доступны обычными REST-ручками (JSON, не RSocket);
- запись требует лишь эхо XSRF-куки в заголовок — клиент вне браузера это умеет.

Контракт `BankPlugin` проверяется вторым по-настоящему иным банком: другой вход
(OIDC), деньги в минорных единицах, явное направление, **операции без привязки к
счёту** (фильтр вместо поля ресурса) и мультивалютный счёт с неуникальным
номером. Где контракт придётся тронуть — покажет спека.
