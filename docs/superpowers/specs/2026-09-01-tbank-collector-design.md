# AIccountant — коллектор операций Т-Банка

Дата: 2026-09-01. Статус: на ревью.

Отдельный под-проект вне дорожной карты этапов. Общая спека:
`docs/superpowers/specs/2026-07-02-aiccountant-design.md`.

## 1. Цель

Забирать операции из личного кабинета Т-Банка автоматически, чтобы не скачивать
выписку руками. Приоритет №1 — **модель безопасности**: сколько секретов
хранится, где и что коллектор физически способен сделать.

Проект личный, но с намерением масштабироваться дальше семьи. Поэтому
переносимость ядра — требование, а не пожелание: то, что мы напишем, должно
переехать в десктоп или мобильное приложение без переписывания.

## 2. Скоуп

Включено:

- Один банк — **Т-Банк**. Ядро («плагин») с логикой этого банка.
- Тонкий локальный раннер, запускающий плагин на машине пользователя.
- Приём операций приложением: новый эндпоинт для **уже разобранных** операций
  и API-токены в `identity` для авторизации коллектора.
- Дедупликация по идентификатору операции от банка.

Явно исключено:

- Другие банки. Форма ядра допускает реестр, но второй плагин не пишем — это
  YAGNI до появления второго реального банка.
- Воспроизведение входа по HTTP (см. §4): логин отдаёт браузер.
- Десктопное и мобильное приложение. Ядро к ним готово, оболочки — нет.
- Категории кешбэка, бонусы, инвестиции — данные в API есть, но в v1 не берём
  (см. §13).

## 3. Модель безопасности

Это первый раздел не случайно: остальное подчинено ему.

### 3.1 Единственный секрет

Разведка показала: для всего data-API достаточно **одной строки** — значения
куки `psid` (~61 символ, непрозрачная). Проверено: запрос **без кук**, только с
`sessionid=<токен>` в query, возвращает данные; без токена — `AUTHENTICATION_FAILED`.

Следствия:

- пароль от банка **не хранится нигде** (его и не спрашивают: вход по телефону
  и коду);
- cookie jar хранить не нужно — только одну строку;
- токен живёт **~24 часа** (`session_status.millisLeft`), после чего бесполезен;
- отозвать = выйти из ЛК.

Хранение: **в персистентном профиле браузера**, который раннер и так заводит для
логина. Куки там шифруются средствами самого браузера через механизм ОС (на
Windows — DPAPI, привязка к учётной записи пользователя). Отдельное хранилище
секретов и нативные зависимости не нужны: раннер при запуске поднимает профиль,
читает `psid` и отдаёт плагину.

Чего **не делаем**: не пишем токен в файл рядом с кодом, в переменные окружения
или в git. Если профиль недоступен — падаем с понятной ошибкой, а не пишем токен
открытым текстом. «Забыть токен» = удалить профиль (команда обязательна).

### 3.2 Ограничение возможностей — технически, а не на доверии

Опасение «непрозрачная программа получила доступ к ЛК и неизвестно, что может»
снимается не обещанием, а проверяемым ограничением: у HTTP-клиента коллектора
**allowlist эндпоинтов**, всё остальное блокируется на уровне транспорта.

Разрешены только:

```
GET /api/common/v1/accounts_light_ib
GET /api/common/v1/session_status
GET /mybank/api/operations/timeline/public/legacy/v1/operations
GET /mybank/api/operations/timeline/public/legacy/v1/operations_category_list_bank
GET /mybank/api/operations/timeline/public/legacy/v1/operations_category_list_user
```

Метод, отличный от `GET`, или адрес вне списка — исключение в самом клиенте, до
отправки. Это покрывается тестом: попытка `POST` и попытка обратиться к
произвольному пути обязаны падать.

### 3.3 Что и где исполняется

Коллектор работает **на машине пользователя**, не на сервере: браузер должен
ходить в банк с домашнего IP и со своим отпечатком, а код из СМС человек вводит
в окно на своём экране. Серверный сбор (вход в банк из датацентра) не
рассматривается — это классический признак угона для антифрода.

### 3.4 Логи и PII

В логи — только идентификаторы и счётчики. Никогда: токен, номер телефона, код
из СМС, описания операций, суммы, номера счетов и карт. Тела ответов банка не
логируются даже при ошибках — только тип ошибки и HTTP-статус.

## 4. Аутентификация: гибрид

Вход в Т-Банк — полноценный OIDC на отдельном домене `id.tbank.ru`:
инициация с `cid`, шаги (телефон → код, возможны кодовое слово, пароль, пуш),
возврат на `www.tbank.ru/auth/` с одноразовым `code` и подписанным сервером
`state` (JWT RS512), обмен через `GET /api/common/v1/session/check_auth`.
По дороге снимается отпечаток устройства.

Воспроизводить это по HTTP **не будем**: протокол с состоянием и ветвлениями,
подписанные сервером параметры, привязка к отпечатку, активная защита. Цена —
недели работы и постоянная поддержка; выигрыш для одного банка не окупается.

**Принятая схема:**

1. Плагин проверяет сохранённый токен через `session_status`.
2. Если токена нет или он протух — оболочка открывает окно браузера на странице
   входа. Человек вводит телефон и код сам; коллектор в форму не вмешивается.
3. После входа оболочка извлекает `psid` и отдаёт плагину.
4. Дальше — **чистый HTTP, браузер не нужен** до следующего протухания.

Переносимость сохраняется: HTTP-часть работает где угодно, а окно логина на
мобильной платформе — WebView, он есть везде.

**Осознанное ограничение:** сессия ~24 часа, значит код из СМС вводится примерно
раз в сутки. Полностью безлюдного сбора не будет. Это приемлемо: история
доступна на годы назад, пропущенный день ничего не теряет.

## 5. Архитектура: ядро и оболочка

Разделение по сроку жизни: ядро переживёт смену платформы, оболочка — нет.

**Ядро — плагин банка.** Чистая логика: получить счета, получить операции за
период, привести к нашей модели. Только HTTP, никакого браузера и никакого
знания о том, куда потом уедут данные. Зависимости: HTTP-клиент с allowlist и
интерфейс «спросить у человека» (для кода из СМС — понадобится, если когда-нибудь
всё же реализуем нативный вход).

**Оболочка — раннер.** Сегодня: локальный процесс, который открывает окно для
логина, извлекает токен, хранит его в хранилище ОС, зовёт плагин и отправляет
результат в приложение. Завтра — тот же плагин внутри десктопа или мобилки.

**Язык ядра — TypeScript.** Он единственный едет во все целевые оболочки: Node
(сегодня), Electron/Tauri (десктоп), React Native (мобилка). Python в мобильное
приложение не поедет. Фронтенд проекта уже на TS, новый стек не заводим.
Бэкенд остаётся питоновым — плагин к нему не относится, это клиентский код.

Расположение: новый каталог `collector/` в корне репозитория, рядом с `backend/`
и `frontend/`. Внутри — `src/plugins/tbank/` (ядро) и `src/runner/` (оболочка),
чтобы граница была видна структурой, а не договорённостью.

## 6. Что отдаёт банк (по результатам разведки)

Факты, а не предположения — всё проверено на живом ЛК.

**Счета** — `GET /api/common/v1/accounts_light_ib`:
12 счетов девяти типов (`Current`, `Credit`, `Saving`, `BNPL`, `CashLoan`,
`SharedCurrent`, `SharedCurrentKids`, `ExternalAccount`,
`OpenBankingCurrentAccount`). Поля: `id`, `name`, `accountType`,
`moneyAmount {value, currency}`, `currency {code, name, strCode}`, `cards[]`.

**Операции** — `GET /mybank/api/operations/timeline/public/legacy/v1/operations`
с параметрами `start`/`end` (epoch-миллисекунды) и опциональным `account=<id>`:

- фильтр по счёту работает;
- пагинации нет: запрос за 10 лет вернул 8285 операций одним ответом;
- поля, которые нам нужны:

| Поле | Смысл |
|---|---|
| `id` | идентификатор операции, уникален — **основа дедупа** |
| `status` | `OK` / `FAILED` |
| `type` | `Credit` / `Debit` — направление |
| `group` | `INCOME` / `INTERNAL` / `LOANREPAY` / `PAY` / `TRANSFER` |
| `isInner` | признак операции между своими счетами |
| `operationTime`, `debitingTime` | `{milliseconds}` — совершение и списание |
| `amount`, `accountAmount` | `{value: float, currency: {...}}` |
| `description` | описание |
| `account` | идентификатор счёта |
| `category`, `spendingCategory` | категория **от банка** |
| `mcc` | код типа торговой точки |
| `merchant`, `brand` | данные о продавце |

**Справочник категорий банка** —
`GET .../operations_category_list_bank`: 90 категорий с `id`, `name`,
`description`.

**Проверка сессии** — `GET /api/common/v1/session_status`:
`millisLeft`, `accessLevel`.

## 7. Отображение в нашу модель

Наш `ParsedOperation` — `occurred_at: date`, `amount: Decimal` (знаковая),
`currency: str`, `description: str`. Правила:

- `occurred_at` — дата из `operationTime` (совершение, не списание), причём
  вычисленная **в зоне Europe/Moscow**, а не в UTC: банк показывает операции по
  Москве, и ночная операция в UTC уехала бы на предыдущий день, а на границе
  месяца — ещё и в чужой месяц статистики расходов. Косвенное подтверждение —
  фронт банка сам передаёт `timeZone=+03:00`;
- `amount` — `accountAmount.value`, знак из `type`: `Debit` → отрицательная,
  `Credit` → положительная;
- `currency` — `accountAmount.currency.strCode`;
- `description` — `description`, при пустом — `merchant.name`;
- `external_id` — **`id` операции от банка** (наш `external_id` ровно для этого
  и заведён: «id от банка, иначе хеш»);
- операции со `status = FAILED` **не импортируем**;
- `isInner` / `group = INTERNAL` в v1 **никак не используем**: переводы между
  своими счетами приезжают обычными знаковыми операциями. Собирать из них пару
  с общим `transfer_group_id` — отдельная задача (см. §13);
- `category`, `mcc`, `merchant` в v1 **не передаём вообще**. Наш эндпоинт приёма
  их не принимает, и добавлять поля «про запас» смысла нет — они появятся вместе
  с фичей, которая их использует (см. §13).

**Деньги.** `amount.value` приходит JSON-числом (float). Правило проекта —
`Decimal` и никогда float, поэтому плагин обязан разбирать ответ парсером,
сохраняющим числовые литералы как строки (`JSON.parse` не годится: он
материализует float до того, как мы что-либо проверим). Тест на потерю
точности обязателен.

**Отложенная авторизация.** Операция может измениться после проведения (сумма
на валютных, описание). Дедуп по `id` от банка это переживает: при повторном
сборе та же операция придёт с тем же `id`. В v1 **обновление уже импортированных
операций не делаем** — только вставку новых; расхождение видно по `debitingTime`
и решается позже (см. §13).

## 8. Приём операций приложением

Коллектор отдаёт **уже разобранные** операции, а не файл. Существующий
`POST /api/imports` принимает PDF и ставит фоновый разбор — этот путь не
подходит.

Добавляем в `imports` эндпоинт для готового разбора:

```
POST /api/imports/parsed?workspace_id=&account_id=
  { "parser": "tbank_collector",
    "operations": [ { occurred_at, amount, currency, description, external_id } ] }
  → 200 { import_id, status: "ready" }
```

Он создаёт запись `Import` со `status=ready` и заполненным `parsed_payload` —
то есть **сразу попадает в существующий конвейер**: превью с дедуп-флагами
(`GET /api/imports/{id}`) и подтверждение (`POST /api/imports/{id}/commit`).
Ни парсер, ни дедуп, ни автокатегоризацию не трогаем.

Суммы в теле запроса — **строками**, как везде на проводе. Вход клиента
валидируется на границе схемы (сумма ненулевая и укладывается в `NUMERIC(20,4)`,
никаких управляющих символов, `external_id` уникальны в пределах запроса) —
иначе ошибка всплывёт уже в ledger и оставит запись импорта в состоянии, где
каждый коммит падает.

**Список ожидающих.** Импорт, созданный коллектором, надо чем-то открыть:
`GET /api/imports` отдаёт разобранные, но не подтверждённые импорты workspace, а
страница импорта показывает их списком с кнопкой «Открыть». Без этого собранные
операции невозможно подтвердить и коллектор бесполезен.

**Сопоставление счетов.** Идентификатор счёта Т-Банка не равен нашему
`account_id`. В v1 соответствие хранится в конфиге коллектора
(`bank_account_id → account_id`), заполняется руками один раз. Хранить это в
БД приложения — задача на потом (см. §13).

## 9. Авторизация коллектора в приложении

Коллектор — не браузер, сессионной куки у него нет. Вводим в `identity`
**API-токены**:

- модель `api_tokens`: `id`, `workspace_id`, `name`, `token_hash`,
  `created_at`, `last_used_at`, `revoked_at`;
- токен показывается **один раз** при создании, в БД — только хеш;
- хеш — **sha256, а не argon2**. Argon2 нужен паролям, потому что они
  низкоэнтропийные и подбираемы; токен же — 32 байта из криптостойкого
  генератора, подбор невозможен. Зато sha256 детерминирован, а значит по нему
  можно искать в индексе за один запрос — с argon2 пришлось бы перебирать все
  токены и сверять каждый;
- передаётся заголовком `Authorization: Bearer <token>`;
- зависимость `require_workspace_member` учит принимать либо сессию, либо токен;
- **токен действует только в том workspace, для которого выдан.** Первая версия
  этой спеки утверждала, что «токен даёт личность, а не доступ ко всем
  workspace» — на ревью выяснилось, что формулировка вводит в заблуждение:
  личность открывает все workspace владельца, а в семейном приложении это ровно
  те, что важны. Область действия проверяется до членства. Инвариант сквозной:
  даже `/api/me` по токену показывает только его workspace, иначе через него
  перечисляются чужие домохозяйства (id, названия, роли);
- **машинный токен не расширяет права.** Утёкшим токеном нельзя создать новый
  токен и нельзя выполнить owner-действия (например, добавить участника) —
  иначе злоумышленник заводит себе учётку, приглашает её в workspace, и отзыв
  токенов перестаёт что-либо решать. Такие действия требуют браузерной сессии;
- создание, список и отзыв — эндпоинтами `/api/tokens`. **Страницы в UI в v1
  нет:** токен создаётся один раз запросом к API, и городить ради этого экран
  преждевременно. Экран появится, когда токенов станет больше одного (см. §13).

Почему токен, а не «бэкенд сам зовёт коллектор»: коллектор обязан жить на машине
пользователя, а бэкенд со временем уедет на сервер и не сможет достучаться до
машины за NAT. Исходящее соединение из дома работает всегда. Токен развязывает
эти два вопроса: сегодня коллектор пушит на `localhost`, завтра — на адрес
сервера, меняется строка в конфиге.

Побочная польза: тот же механизм понадобится Telegram-боту из дорожной карты.

## 10. Поток работы и ошибки

```
раннер: есть сохранённый токен?
   ├─ нет / протух  → открыть окно логина → человек вводит телефон и код
   │                   → извлечь psid → сохранить в хранилище ОС
   └─ да            → дальше
плагин: получить счета → получить операции за период → привести к нашей модели
раннер: POST /api/imports/parsed  → показать пользователю import_id и счётчики
человек: смотрит превью в UI и подтверждает импорт
```

Период по умолчанию — последние 30 дней (перекрывает пропуски; дубли отсекутся
по `external_id`). Первичный импорт истории — отдельный запуск с явным периодом.

Ошибки:

- **токен протух посреди сбора** → `AUTHENTICATION_FAILED` от банка: раннер
  сообщает «нужен вход», не пытается ничего обойти;
- **банк недоступен / таймаут** → сбор не состоялся, ничего не отправляем,
  повтор при следующем запуске;
- **приложение недоступно** → операции уже собраны; раннер сообщает об ошибке
  и не теряет их молча (повторный сбор дешёв, поэтому в v1 не кэшируем);
- **allowlist сработал** → это баг в нашем коде, падаем громко, не «чиним» обход.

Подтверждение импорта остаётся **ручным**: коллектор доводит до превью, решение
за человеком. Автокоммит — осознанно не в v1.

## 11. Тестирование

- **Плагин** — на записанных ответах банка (как контрактные тесты LLM в проекте).
  Сеть в тестах не дёргаем. Записи очищены от PII: суммы и описания заменены,
  идентификаторы синтетические.
- **Отображение** — знак по `type`, пропуск `FAILED`, `external_id` = `id`
  банка, дата из `operationTime`.
- **Деньги** — тест на потерю точности: число с большим количеством разрядов
  проходит через разбор без искажения; `JSON.parse` в этом тесте должен падать,
  наш парсер — нет.
- **Allowlist** — `POST` и произвольный путь обязаны бросать исключение.
- **Хранение токена** — сохранение, чтение, «забыть»; токен не появляется в
  логах (тест на содержимое лога).
- **Бэкенд** — `POST /api/imports/parsed`: создаёт `ready`-импорт, изоляция по
  workspace, дедуп по `external_id` при повторной отправке; API-токен: принимается,
  отозванный отвергается, чужой workspace не виден.

## 12. Принятые развилки

- Один банк. Реестр парсеров не строим до второго реального банка.
- Вход — через браузер, извлечение токена; OIDC не воспроизводим.
- Единственный секрет — строка сессии, в хранилище ОС; пароль не хранится нигде.
- Возможности ограничены allowlist'ом GET-эндпоинтов — проверяемо, а не на слово.
- Ядро на TypeScript ради переносимости в десктоп и мобилку.
- Коллектор пушит в API по токену (не «бэкенд зовёт коллектор») — это развязывает
  расположение бэкенда от расположения коллектора.
- Дедуп по идентификатору операции банка, а не по хешу.
- Импорт подтверждает человек.

## 13. Открытые вопросы и будущее

- **Категории кешбэка.** В API есть `cashback`, `cashbackAmount`, `loyaltyBonus`,
  `loyaltyPayment`, а также справочник категорий банка. Просится отдельной фичей:
  видеть, где сколько вернулось и какие категории кешбэка активны. В v1 не берём.
- **Категория и MCC от банка.** Данные забираем, но не применяем. Логично сделать
  их источником категории вместо LLM для Т-Банка — но это меняет этап 2a
  (приоритет источников категории, маппинг 90 категорий банка на наши), поэтому
  отдельным под-проектом.
- **Парность переводов.** `group=INTERNAL` / `isInner` позволяют собрать пару
  строк перевода в наш `transfer_group_id`. В v1 импортируем как обычные
  знаковые операции.
- **Обновление изменившихся операций.** Холд → проведение может поменять сумму.
  Дедуп по `id` защищает от дублей, но обновление существующей операции v1 не
  делает. Нужен ли — покажет практика.
- **Экран управления токенами** в UI: пока их один, хватает API. Появится вместе
  со вторым потребителем (Telegram-бот).
- **Сопоставление счетов** живёт в конфиге коллектора. Если счетов станет много
  или коллекторов несколько — переносить в БД приложения.
- **Open Banking.** Т-Банк агрегирует счета других банков
  (`OpenBankingCurrentAccount`), и операции по ним приходят тем же эндпоинтом —
  проверено, 27 операций за 90 дней. Потенциально один коллектор закрывает
  несколько банков без единой новой строки кода. Проверить на практике.
- **Срок сессии.** ~24 часа. Если окажется, что он продлевается активностью,
  режим «ввожу код раз в сутки» смягчится.
- **Масштаб.** Локальный коллектор — решение для одного пользователя. Для
  продукта на десятки людей потребуется сбор на устройстве пользователя внутри
  клиентского приложения (путь Дзен-мани). Ядро к этому готово, оболочка — нет.
