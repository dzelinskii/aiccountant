# AIccountant — этап 2b «LLM-парсер произвольных выписок (PDF, async)»

Дата: 2026-07-10. Статус: на ревью.

Под-проект этапа 2 (AI-конвейер), идёт после 2a (AI-автокатегоризация, смержено,
PR #8). Общая спека: `docs/superpowers/specs/2026-07-02-aiccountant-design.md`
(раздел 5.4 «Парсинг документов»). Опирается на модуль `ai` из 2a
(`LLMClient`) и модуль `imports` из 1.2b2 (детерминированный парсер Т-Банка).

## 1. Цель

Импортировать банковские выписки **любых банков**, а не только Т-Банка. Формат
выписки распознаётся алгоритмически (набор детерминированных парсеров под
конкретные банки); если ни один не подошёл — разбор через LLM (текст → строго
типизированный JSON, валидация кодом). Разбор может быть медленным (LLM), поэтому
импорт становится асинхронным (Celery).

Скоуп v1 — **только PDF с текстовым слоем**. CSV, сканы/OCR — не сейчас.

## 2. Скоуп

Включено:

- Абстракция `StatementParser` (Protocol: `detect` + `parse`) и реестр
  парсеров; роутер «детерминированные по очереди → LLM-фолбэк».
- Оборачивание существующего парсера Т-Банка в `StatementParser`.
- `LLMStatementParser` — фолбэк: извлечённый текст → `ai.LLMClient` →
  типизированный JSON → валидация кодом → `ParsedStatement`.
- Единый асинхронный поток импорта через Celery: загрузка → задача разбора →
  сохранённый результат → превью → коммит из сохранённого (парсим один раз).
- Редизайн API импорта: `POST /api/imports` (старт), `GET /api/imports/{id}`
  (статус/превью), `POST /api/imports/{id}/commit`.
- Миграция `0007`: `parsed_payload`/`error`/`parser` в `imports`.
- Frontend: страница «Импорт» на async (поллинг статуса, бейдж «чем разобрано»,
  предупреждения, ошибка).
- Конфиг `LLM_MODEL_PARSE` и кап на размер текста.
- import-linter: `imports → ai` разрешён; `ignore_imports` ребра
  `imports.tasks -> app.core.celery_app`.

Явно исключено (позже):

- CSV, сканы/OCR, vision-модели.
- Чанкинг больших выписок в несколько LLM-вызовов (v1 — один вызов + кап).
- Вебсокеты для статуса (v1 — поллинг).
- Автоопределение счёта по реквизитам выписки (счёт выбирает пользователь).
- Новые детерминированные парсеры под другие банки (архитектура готова, но в v1
  детерминированный парсер один — Т-Банк; остальное покрывает LLM-фолбэк).

## 3. Архитектура парсинга

`StatementParser` (Protocol):

- `detect(text: str) -> bool` — распознаёт ли парсер этот формат (дёшево, по
  устойчивым маркерам шапки/структуры);
- `parse(text: str) -> ParsedStatement` — разбирает; при неверном формате
  бросает `StatementParseError`.

`ParsedStatement`/`ParsedOperation` — как сейчас (`operations`, `total_income`,
`total_expense`; операция: `occurred_at: date`, `amount: Decimal` знаковая,
`currency: str`, `description: str`).

Реестр и роутер (чистая функция, без БД/сети, кроме вызова LLM внутри
LLM-парсера):

```
DETERMINISTIC = [TBankStatementParser(), ...]      # порядок фиксирован
def route(text) -> (ParsedStatement, parser_name):
    for p in DETERMINISTIC:
        if p.detect(text):
            return p.parse(text), p.name
    return LLMStatementParser(llm).parse(text), "llm"
```

- `TBankStatementParser`: `detect` — по устойчивым маркерам справки Т-Банка
  (шапка/колонки/итоги); `parse` — существующая `parse_statement`.
- Извлечение текста из PDF (`extract_lines`/pypdf) остаётся тонким слоем,
  выполняется до роутера (роутер работает с текстом).

## 4. LLM-парсер и валидация

`LLMStatementParser.parse(text)`:

1. Вызов `ai.LLMClient.complete_json(system, user)` с инструкцией вернуть строго:
   ```json
   {"operations": [{"occurred_at": "YYYY-MM-DD", "amount": "-1150.00",
     "description": "..."}], "total_income": "5000.00", "total_expense": "1150.00"}
   ```
2. Разбор JSON → Pydantic-модель. Суммы и итоги — **строки**, парсятся в
   `Decimal` кодом (знак сохраняется); `float` не используется нигде. Дата — ISO
   → `date`. `currency` берётся из счёта импорта (одновалютный MVP — RUB), в
   ответе LLM не требуется.
3. Доменная валидация:
   - **Жёсткие ошибки** → `StatementParseError` (в задаче → `status=failed`,
     ничего не импортируется): невалидный/непарсящийся JSON, ноль операций,
     непарсящиеся дата/сумма, сумма == 0.
   - **Мягкие** → возвращаем `ParsedStatement`, но с предупреждением: расхождение
     контрольной суммы (`sum(amount>0)` ≠ `total_income` и т.п.) или отсутствие
     итогов. Пользователь решает, коммитить ли. Это поведение уже принято для
     детерминированного пути (`import_control_sum_mismatch` — сигнал, не отказ).

Модель: `LLM_MODEL_PARSE` (конфиг; может совпадать с базовой). Фабрика
`ai.build_llm_client` принимает модель параметром. Слой `ai` остаётся
доменно-независимым (парсинг-промпт живёт в `imports`, не в `ai`).

Кап на размер: `IMPORT_MAX_TEXT_CHARS` (конфиг). Текст крупнее — `status=failed`
с сообщением «выписка слишком большая для авто-разбора».

## 5. Данные и async-поток

Миграция `0007` — в таблицу `imports`:

- `parser` `VARCHAR(30) NULL` — какой парсер сработал (`tbank_statement`/`llm`);
- `parsed_payload` `JSONB NULL` — разобранные операции + итоги + предупреждения
  (заполняется задачей; коммит читает отсюда — **перепарсивания нет**);
- `error` `VARCHAR(500) NULL` — сообщение при `status=failed` (длинные обрезаем);
- `raw_text` `TEXT NULL` — текст выписки для фоновой задачи; отдельной колонкой,
  а не внутри `parsed_payload`, чтобы очищать сразу после разбора (PII).

`status` (уже есть) — значения `processing` | `ready` | `failed`
(вместо прежнего единственного `completed`; при коммите — `imported`... нет:
оставляем `ready` до и после коммита, факт импорта — по созданным операциям и
`stats`; отдельный статус для «закоммичено» не заводим ради простоты).

Поток:

1. `POST /api/imports?workspace_id=&account_id=` (multipart PDF): проверить
   тип/размер файла и принадлежность счёта; извлечь текст (`extract_lines`);
   создать `Import(status=processing)` с сырым текстом в `raw_text`;
   поставить задачу; вернуть `202 {import_id, status}`.
2. Задача `imports.parse_statement_job(import_id)`: загрузить текст → `route(text)`
   → валидация → записать операции/итоги/предупреждения в `parsed_payload`,
   `parser`, `status=ready`; при `StatementParseError`/ошибке → `status=failed`,
   `error`. Логи — только идентификаторы.
3. `GET /api/imports/{id}?workspace_id=`: при `ready` — превью
   (операции с дедуп-флагом, `new_count`/`duplicate_count`, итоги, `parser`,
   `warnings`); при `processing` — статус; при `failed` — `error`.
   Дедуп считается на лету: `external_id` по сохранённым операциям vs уже
   импортированные (запрос к ledger).
4. `POST /api/imports/{id}/commit?workspace_id=`: из `parsed_payload` создать
   только новые операции (`source=import`, `category_id=null`, `external_id`,
   `import_id`), обновить `stats`, один commit; поставить автокатегоризацию
   (этап 2a). Идемпотентно: повторный коммит отсекается дедупом.

## 6. Границы модулей и инфраструктура

- `LLMStatementParser` (в `imports`) зовёт `ai.LLMClient` — направление
  `imports → ai` разрешено (как `ledger → ai`).
- Новый `imports/tasks.py` (Celery) импортирует `core.celery_app` — транзитивный
  путь через регистрацию моделей (как у `ledger.tasks`/`recurring.tasks`);
  добавляем `ignore_imports = ["app.imports.tasks -> app.core.celery_app"]` в
  контракт «imports не лезет во внутренности identity и ledger».
- `core.celery_app`: `autodiscover_tasks([... , "app.imports"])`, добавить импорт
  `app.imports.models` в блок регистрации моделей.
- Дедуп `external_id` не меняется.

## 7. Frontend

Страница «Импорт» на async:

- Загрузка файла → `POST` → `import_id`; состояние «Разбираем выписку…» с
  поллингом `GET /imports/{id}` (интервал ~1.5 с).
- `ready` → таблица превью (дата, сумма строкой, описание, бейдж новая/дубль),
  счётчики новых/дублей, итоги, **бейдж чем разобрано** («Т-Банк»/«AI-разбор»),
  жёлтое предупреждение при расхождении контрольной суммы → кнопка
  «Импортировать N новых» (`POST /commit`).
- `failed` → понятная ошибка + возможность загрузить другой файл.
- После коммита — обновление лент/дашборда (категоризация подхватится сама).

## 8. Ошибки и приватность

- LLM недоступен/таймаут/битый JSON, превышение капа → `status=failed` с
  сообщением; не молча. Лог — только идентификаторы (без PII/сумм).
- Сырой текст выписки — PII: живёт в `Import.parsed_payload` только на время
  разбора; после `ready` там разобранные операции; сырой текст очищается при
  коммите. Реальные файлы в git не коммитим (уже `.gitignore`).
- Задача идемпотентна по `import_id`; частичный сбой не оставляет полу-импорта
  (операции создаются в одном commit на шаге commit, не в задаче разбора).

## 9. Тестирование

- **Юнит (в CI, без сети):** роутер (`detect`→выбор; никто не подошёл→LLM);
  `TBankStatementParser.detect` на тексте реального формата и на чужом;
  `LLMStatementParser` на **записанных** ответах LLM (валидный разбор; битый JSON
  → `StatementParseError`; расхождение контрольной суммы → warning); валидация
  Pydantic (строки→`Decimal`, знак, дата, сумма==0).
- **Async-поток:** задача `processing→ready/failed`, `parsed_payload` заполнен;
  `GET` отдаёт превью/статус/ошибку; `commit` создаёт операции из сохранённого
  разбора + дедуп + ставит категоризацию (мок брокера/LLM).
- **Изоляция workspace** на всех новых эндпоинтах; **контрактный тест
  LLMClient**; import-linter (imports→ai ок, ai ни от кого; 8-й контракт/ignore).
- Существующие тесты Т-Банка адаптируются к async-потоку (парсер тот же).

## 10. Принятые развилки

- Форматы v1 — только текстовый PDF; CSV/OCR — позже.
- Реестр детерминированных парсеров (по одному на банк) + LLM-фолбэк; выбор
  автоматический, не пользователем.
- Единый асинхронный поток через Celery; парсим один раз, коммит — из
  сохранённого разбора.
- Валидация: жёсткие ошибки → `failed`; мягкие (контрольная сумма/итоги) →
  предупреждение, решает пользователь.
- LLM-парсер в `imports`, зовёт `ai.LLMClient`; `ai` доменно-независим.
- Отдельная модель `LLM_MODEL_PARSE`; кап на размер текста.

## 11. Открытые вопросы

- Значение капа `IMPORT_MAX_TEXT_CHARS` и выбор модели уточняются на реальных
  выписках других банков; чанкинг больших выписок — при необходимости. Дефолт
  сознательно консервативный (20000): ответ модели тоже ограничен по длине, а
  обрезанный JSON выглядит как «непонятный ответ» вместо честного «выписка
  слишком большая». Ограничение выхода (`max_tokens`) и чанкинг — когда появятся
  реальные многостраничные выписки чужих банков.
- Поллинг статуса, не вебсокеты (проще для v1).
- Точность LLM-разбора на незнакомых форматах меряется вручную на реальных
  выписках; формальный eval-набор разбора — при появлении нескольких образцов.
- Очистка сырого текста/разобранных операций после успешного импорта — политика
  хранения уточняется (сейчас: сырой текст чистим при коммите).
- Лимит 10 МБ в роутере проверяется ПОСЛЕ того, как Starlette дописал тело в
  `SpooledTemporaryFile` (RAM ограничена ~1 МБ, но диск — нет). Значит гигантский
  аплоад упрётся в 413 только после записи на диск. Настоящий заслон — лимит тела
  запроса в Caddy (`request_body { max_size 10MB }`); сейчас его нет. Сделать при
  подготовке деплоя.
- Фоновые задачи ходят в БД через отдельный движок **без пула**
  (`worker_session_factory`): Celery выполняет каждую задачу в своём event loop
  (`asyncio.run`), а пул хранит соединения, привязанные к уже закрытому циклу —
  каждый второй запуск падал. Найдено при ревью этапа 2b, чинит заодно уже
  смерженные `ledger.categorize_workspace` и `recurring.scan_due`.
- Худший случай LLM-вызова (таймаут × попытки) обязан укладываться в порог
  reaper'а `STUCK_AFTER`, иначе тот добьёт живой разбор. Связь охраняется
  тестом-инвариантом, а не комментариями.
- Застрявшие в `processing` импорты (воркер умер, сообщение потеряно) добивает
  периодическая beat-задача `imports.reap_stuck`: ставит `failed` с понятным
  текстом и стирает `raw_text`. Без неё гарантия «сырой текст живёт только до
  конца разбора» не выполняется, а фронт поллит запись вечно.
- Лишние ключи в ответе LLM игнорируются (не `extra="forbid"`): ронять весь
  импорт из-за одного лишнего поля хрупко. Побочный эффект: если модель вернёт
  `"currency": "USD"`, ключ молча отбрасывается и операция штампуется RUB. Сейчас
  это соответствует одновалютному MVP, но при вводе мультивалютности сюда надо
  вернуться в первую очередь.
- Детект Т-Банка строгий: заголовок «Движение средств за период» ИЛИ **оба**
  итога сразу. Поэтому справка без заголовка и всего с одним итогом (например,
  за период без пополнений) уйдёт в LLM — дороже, но безопаснее частичного
  разбора чужой выписки, которую одиночное «Расходы:» заставило бы claim'ить.
