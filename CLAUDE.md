# AIccountant — правила проекта

AI-бухгалтер для домохозяйства: чтение финансовых документов, сверка,
аномалии, прогноз. Дизайн и дорожная карта:
`docs/superpowers/specs/2026-07-02-aiccountant-design.md` — сверяться с ней
перед крупными изменениями; решения из раздела «Принятые развилки»
не пересматривать молча.

## Структура репозитория

- `backend/` — FastAPI, модульный монолит (Python 3.12+, uv)
- `frontend/` — React 18 + TypeScript + Vite (pnpm), Mantine, PWA
- `infra/` — docker-compose, Caddy, деплой
- `docs/` — спеки, планы, ADR

## Архитектурные правила

- Модули backend: `identity`, `ledger`, `recurring`, `imports`, `ai`. Задуманы
  ещё `analytics` и `notifications` — их пока нет. Общение — только через
  сервисные интерфейсы; в таблицы чужого модуля не ходить (контролируется
  import-linter, текущие контракты — в `docs/reference/generated/`).
- Все доменные таблицы несут `workspace_id`; каждый запрос фильтрует по нему
  в repository-слое. Утечка данных между workspace — критический баг.
- Деньги — `NUMERIC(20, 4)` в БД и `Decimal` в коде. `float` для денег
  запрещён везде, включая тесты; на фронте суммы передаются строками.
- LLM/эмбеддинги/распознавание речи — только через интерфейсы модуля `ai`
  (`LLMClient`, `EmbeddingClient`, `Transcriber`). Вендорские SDK
  не импортировать за пределами реализаций этих интерфейсов.
- Фоновая и периодическая работа — Celery/beat. Доменная логика не живёт
  во внешних инструментах.
- Схема БД меняется только через миграции Alembic.

## Тулинг и качество

- Python: uv, ruff (линт и формат), mypy (strict), pytest + pytest-asyncio,
  testcontainers для интеграционных тестов.
- TypeScript: pnpm, eslint + prettier, vitest.
- Тесты обязательны для доменной логики и краевых случаев. LLM-фичи —
  контрактные тесты на записанных ответах; категоризация — eval-набор
  с метрикой точности.
- Перед «готово» — линт, типы и тесты прогнаны, результат подтверждён.

## Процесс

- Деплой не блокирует переход к следующему этапу. Разворачиваем, когда владелец
  решит, что проект дорос до состояния, в котором им можно хотя бы частично
  удобно пользоваться. До этого момента демо-URL не заводим и в README его не
  обещаем.
- Этап всё равно описывается в README по мере готовности — чтобы репозиторий
  не расходился с тем, что в нём лежит.
- В логи не писать PII и суммы — только идентификаторы.

## Справочник

`docs/reference/` описывает **состояние** системы; спеки в
`docs/superpowers/specs/` — **изменения** на свою дату. Расходятся с кодом —
прав код, а справочник надо чинить.

- Меняете поведение — правьте справочник в том же изменении. CI это требует:
  правка `*/service.py`, `app/core/*`, `collector/src/core/*` или
  `plugins/*/map.ts` без правки `docs/reference/` красит сборку. Снимается
  меткой `docs-not-needed` на PR, если правка и правда поведения не меняет.
- Генерируемую часть (`docs/reference/generated/`) руками не править: её
  перезаписывают `uv run python scripts/gen_reference.py` и `pnpm reference`,
  а CI сверяет с кодом.
- В бриф ревьюера-субагента включать сверку справочника с дифом: описывает ли
  он то, что код делает теперь, а не то, что делал раньше. Генерация и ворота
  этого не ловят — они видят факт правки, а не её смысл.
- Писать справочник по памяти нельзя, только по коду. Проверено на практике:
  из трёх утверждений, записанных по памяти о собственной же работе, неверными
  оказались все три.
